Rocky × CloudLabs · Component & Deployment Design

The On-VM Agent for whole-Windows-VM awareness

A first-party agent baked into the CloudLabs Windows image — perceiving the desktop via UI Automation, reasoning in-tenant, and rendering Rocky as an always-on-top overlay the learner sees inside the RDP video.

00 The constraint that decides everything

"RDP-over-browser" means the RDP client is a server, not the learner's PC

Before choosing a single component, one fact has to be nailed down, because it inverts the obvious answer. CloudLabs delivers the VM as HTML5 in the browser. There is no mstsc.exe on the learner's machine. The browser speaks a JS/WebSocket protocol to a server-side gateway (the confirmed-unconfirmed backend is abstracted behind a per-learner launch URL, but the dominant open-source pattern — and the realistic assumption — is Apache Guacamole's guacd driving FreeRDP).1

So the "RDP client" that terminates the protocol is guacd running in CloudLabs infrastructure. That has a hard consequence the rest of this document is built around:

Why the "obvious" DVC path is the harder one

Microsoft's clean Dynamic Virtual Channel APIs (IWTSPlugin, registered under HKCU\…\Terminal Server Client\Default\AddIns) are client-side plug-ins for the native RDC/mstsc client.2 In a browser-delivered session that client doesn't exist. A DVC here would have to be a compiled FreeRDP add-in living in guacd, and FreeRDP exposes no documented runtime API to register a custom channel without shipping a separate .so in its plugin directory.3 DVC is therefore possible but it is platform-team surgery on the remoting tier — not a thing the VM image alone can deliver.

This is the honest version of the trade-off most "RDP companion" pitches gloss over. The recommendation below leads with the path that is actually shippable from the image, and treats DVC as a later optimization gated on platform work.

Why this split, component by component

Lifecycle owner — a Windows Service, not a tray app

A Service starts at boot before any user logs in, survives the learner killing things, and can run a watchdog + auto-update. But a Service lives in Session 0 and cannot display UI — Microsoft's guidance is explicit and longstanding: "services cannot directly interact with a user as of Windows Vista … a service cannot display a user interface item such as a dialog box directly."4 The documented pattern is exactly what we use: a service plus "a separate … GUI application … run within the context of the interactive user," talking over IPC.4

The visible companion — a per-session UI process the service launches

The overlay and the avatar live in a normal interactive process running as the learner, in WinSta0\default. The service resolves the active session with WTSGetActiveConsoleSessionId / session-notification callbacks and launches the UI process there with CreateProcessAsUser.4 Registering the UI app under HKLM\…\CurrentVersion\Run is the documented backstop so it also starts on a fresh interactive logon.4

Could the overlay just be a tray/startup app with no service?

Yes, and for a first prototype that is the fastest route — skip the service entirely, ship only the per-session UI process via Run key or Startup folder. You lose: pre-logon presence, a privileged watchdog, and a clean update channel. Recommendation: prototype as UI-process-only; promote to service+UI for production because update/repair on an imaged fleet is the real operational problem (see §6).

02 Rendering Rocky onto the desktop the learner sees

An always-on-top, per-pixel-alpha layered window — composited before RDP captures the frame

The overlay does not need to know anything about RDP. It draws onto the VM desktop; the remoting tier captures that desktop and streams it. If it looks right locally, it looks right in the browser.

This is the key insight that makes the overlay tractable: RDP/Guacamole streams whatever is composited on the VM's desktop. A top-most window on the VM is, by definition, in the captured frame. We are not compositing into a video stream client-side — we are putting a window on a desktop and letting the existing capture path do its job.

The window recipe

GoalMechanismNotes
Floats above all appsWS_EX_TOPMOSTTopmost windows sit ahead of all non-topmost windows in z-order regardless of focus.6
Shaped, soft-edged, anti-aliased avatar (not a rectangle)WS_EX_LAYERED + UpdateLayeredWindowPer-pixel alpha. Preferred over SetLayeredWindowAttributes for a complex/animated shape; uses memory more efficiently and avoids the redirection buffer.7
Clicks pass through to the app underneathWS_EX_TRANSPARENTSee hit-testing below — this is the load-bearing detail.
Never steals focus / no taskbar buttonWS_EX_NOACTIVATE + WS_EX_TOOLWINDOWAvatar must not become the foreground window or the UIA "focused element" it is trying to read.

Click-through and hit-testing — the part people get wrong

For a layered window, Windows hit-tests against the window's shape and transparency: pixels that are color-keyed or have alpha = 0 already let the mouse through.7 So a per-pixel-alpha avatar is naturally click-through everywhere it's invisible — no extra work. But over the opaque avatar pixels you have a binary choice, and you want both behaviors at different times:

  • Passive avatar (default): add WS_EX_TRANSPARENT. Then "the shape of the layered window will be ignored and the mouse events will be passed to other windows underneath"7 — the learner can click straight through Rocky to the Azure Portal button he's pointing at. This is the correct default: Rocky must never block the lab.
  • Interactive moment (learner clicks Rocky to chat): toggle WS_EX_TRANSPARENT off so the avatar body receives clicks, or — cleaner — keep the avatar click-through and put the chat affordance in a small, separately-hittable child region. Recommended: a "hot zone" model, so the bulk of Rocky stays click-through and only a deliberate handle is interactive.

Pitfall — the input-vs-pixels asymmetry over RDP

The overlay's pixels are composited on the VM and travel in the RDP video automatically. The overlay's input handling is purely local Win32 — the browser sends mouse coordinates to guacd, which injects them into the VM session, and only then does Windows hit-test the layered window. So click-through "just works," but it means Rocky cannot intercept input before the app does unless it is the non-transparent foreground window — which we deliberately avoid. Consequence: the on-VM agent observes and advises; any "Rocky clicks for you" (P4) must go through a separate, consented automation path, not by eating mouse events under the overlay.

Multi-monitor, DPI, and the RDP resize problem

A browser RDP session resizes constantly — the learner resizes the tab, the gateway renegotiates the remote resolution, and the "monitor" the VM sees changes shape mid-session. The overlay must be robust to this or it will drift off-screen or render blurry.

  • Declare Per-Monitor-v2 DPI awareness (DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2). PMv2 is the only mode where the whole window tree — top-level and child windows — is notified of DPI changes, and the app is never bitmap-stretched (i.e., never blurry).8
  • Handle WM_DPICHANGED by re-rendering the avatar at the new scale and repositioning to the suggested rect — do not assume a one-time layout at startup; the docs call this out explicitly.9
  • Re-anchor on resolution change. Listen for WM_DISPLAYCHANGE / monitor-topology changes and re-pin Rocky to a corner expressed as a fraction of the work area, recomputed against the current monitor via GetDpiForWindow / GetSystemMetricsForDpi rather than cached system metrics.8
  • Multi-monitor labs: a remote session can present multiple monitors; pin to the primary work area and clamp the avatar rect to the intersection of the visible monitors so it can't strand itself on a monitor the learner closed.

03 Communications — how the pieces talk

Recommended path: agent → cloud WebSocket. DVC is a deferred optimization.

Three links exist: in-VM IPC (service ↔ UI process), VM ↔ reasoning service, and browser-page ↔ agent. The middle one is where the real design decision is, and the browser-delivered model settles it.

Recommendation

Ship on an outbound agent→cloud WebSocket. It decouples Rocky from a remoting backend that is itself unconfirmed, it's the same transport the Cosmos learner-facing agent already needs, and it sidesteps the FreeRDP-add-in dependency entirely. The browser page and the overlay coordinate through the reasoning service (both authenticate to the same lab session), not directly — so "Ask Rocky" in the guide pane and the on-desktop avatar stay in sync via shared session state, with no fragile cross-origin bridge. Revisit DVC only if (a) egress proves problematic in a customer tenant, or (b) the platform team is already opening the FreeRDP tier for other reasons — then DVC becomes a latency/egress optimization, not a prerequisite.

04 Getting lab / validation context

The desktop tells you "what" — CloudLabs APIs tell you "what it's supposed to be"

Per ADR-002 the on-VM perception is the fallback/enrichment tier, not the primary. The agent's value comes from joining the redacted screen summary with the structured intent + correctness signals CloudLabs already exposes. The reasoning service — not the VM — pulls these, scoped to the lab session:

  • Guide structure + current step — what the learner is supposed to be doing. (labGuide/…/partner-lab-guide; current-step needs the proposed Runtime Context API.)
  • Validation results — pass/fail per step, the ground truth for "did it work." (…/users/{eventUserGuid}/validation-results, on-demand POST …/validate.)
  • Deployment diagnostics — cloudlabs_deployment_activity_log for provisioning errors the learner can't see.
  • Per-user OpenAI credit — read/respect/extend existing rails (sync-open-ai-credit) so the overlay inherits the lab's cost model (BC-001).

The on-VM agent carries a lab-session-scoped, least-privilege token (SC-003), correlated to eventUserGuid/deploymentGuid, so the reasoning service can fetch context for this learner only. The VM never holds cloud credentials or calls CloudLabs APIs directly — it only emits redacted observations upward.

All endpoint names are from prior firsthand platform research (research/cosmos_session_2026-06-30) and remain unconfirmed against live API docs. The "current step" and a runtime event bus do not exist yet and are the top platform asks (architecture.md §3).

05 Packaging, image baking, updates, least privilege

The agent ships in the image; its brain ships in the cloud

Because CloudLabs owns and images the VM (the premise that makes this feasible at all), the agent install is a known, controlled step — but updating an imaged fleet is the operational hazard, so keep the in-VM binary thin and dumb.

Bake into the image

Install the service + UI app during golden-image build (MSI/MSIX, or a provisioning script in the image pipeline). Service: auto-start, delayed. UI app: registered under HKLM\…\Run for interactive-logon start.4 No per-lab install step at launch.

Keep the binary thin

Prompts, models, tool definitions, and lab knowledge live in the cloud reasoning service — not in the image. Updating Rocky's behavior then needs no image rebake. The in-VM code is just: perceive, redact, transport, render. Version it and let it self-report.

Update channel

The service checks a signed manifest on startup/interval and self-updates the in-VM binaries out-of-band, so a bug fix doesn't wait for the next golden-image cycle. New images pick up the latest at bake time; running fleets get it via the service. Sign everything; pin the update host.

Least privilege

UI process runs as the learner, no elevation — UIA reading and an overlay need no admin. The service runs at the lowest right that still lets it CreateProcessAsUser into the session and self-update; avoid LocalSystem drawing on the interactive desktop (MS warns this exposes the service to anything the learner runs).4

Privacy & consent are gating, not optional (SC-001/002)

An on-VM agent that reads the foreground window's accessibility tree is, to an enterprise buyer, a keylogger-shaped thing until proven otherwise. Non-negotiables: a telemetry-only / no-screen-capture mode where the OCR fallback is hard-disabled (SC-001); disclosed, consented observation with a visible "Rocky is watching this step" state and a one-click dismiss (SC-002, UX-002); redaction before egress (SC-005); and the character-off skin for enterprise (UX-001). This is exactly why ADR-004 ranked P3 as high-risk and deferred it behind P1/P2. This design does not change that risk verdict — it makes the in-VM tier buildable when the org chooses to clear that gate.

06 Consolidated pitfalls

What bites you in build, not in the slide deck

!

Assuming a mstsc DVC plug-in works

It's a server-side FreeRDP add-in in a browser-delivered session. Don't design comms around DVC; lead with outbound WSS.23

!

Trying to draw UI from the Service

Session 0 isolation: services cannot show UI. You must have a separate per-session UI process and IPC.4

!

Overlay stealing focus or polluting UIA

Without WS_EX_NOACTIVATE, Rocky becomes the foreground/focused element and corrupts the very perception it's trying to do. Tool-window + no-activate.

!

Forgetting click-through, or making it global

Default WS_EX_TRANSPARENT so Rocky never blocks a lab control; carve out one hittable handle for "chat." Don't toggle transparency on the whole window per-frame.7

!

System-DPI awareness → blur on resize

Browser RDP resizes constantly; System-aware windows get bitmap-stretched and go blurry. Declare PMv2 and handle WM_DPICHANGED.89

!

UIA cross-user / cross-integrity gaps

UIA "does not enable communication between processes started by different users,"5 and elevated apps may be unreadable from a non-elevated client. Run the reader as the learner; expect blind spots on elevated installers/UAC — that's where the OCR fallback earns its place.

!

UIA latency on huge trees

A full desktop walk can touch thousands of elements; MS says fetch only direct children and start from the foreground window, use cached requests/FindFirst, not a blind FindAll from root.10

!

Updating a baked fleet

If behavior lives in the image, every prompt tweak is a rebake. Keep the binary thin; put the brain in the cloud service; give the in-VM service a signed self-update path.

07 The recommendation in one breath

Recommended architecture

A Windows Service (lifecycle, update, launch) + a per-session learner-context UI process that hosts a UI-Automation reader (OCR fallback, off by default) and an always-on-top, per-pixel-alpha layered window (WS_EX_TOPMOST | WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE, PMv2 DPI) that renders Rocky onto the VM desktop the RDP gateway already captures. The UI process talks to a cloud Rocky Reasoning Service over an outbound WebSocket, sending redacted screen summaries and receiving render/speech instructions; that service joins the screen context with CloudLabs guide/validation APIs and coordinates with the existing guide-pane Rocky through shared lab-session state. DVC is deferred — it needs a FreeRDP add-in on the remoting tier and buys nothing the WebSocket doesn't, until egress or platform direction changes. Privacy mode, consent, redaction, and the enterprise character-off skin are build gates, consistent with ADR-004's high-risk verdict on the in-VM tier.
