Short answer: partially, but not as a real-time activity feed of “what the learner is doing right now” inside the lab UI.

What appears to exist today in CloudLabs is:

A lab progress read API:
GET /api/partners/{partnerGuid}/labs/{ondemandLabGuid}/progress/users/{eventUserId}
Summary: “Gets the lab progress detail.”
A progress summary / leaderboard API:
POST /api/partners/{partnerGuid}/labs/{ondemandLabGuid}/progress/summary
Summary: “Gets the lab progress leaderboard.”
A template validation-definition API:
GET /api/partners/{partnerGuid}/templates/{templateGuid}/template-lab-guide-validations
Summary: “Gets the template lab guide validations.”
Lab guide content/association APIs that can help you retrieve the guide structure:
GET /api/partners/{partnerGuid}/labGuide/{labGuideGuid}/partner-lab-guide
GET /api/partners/{partnerGuid}/labGuide/{templateGuid}/template-lab-guides/{onDemandLabGuid}

What this likely means in practice:

You can probably retrieve progress state for a learner at the lab / exercise / validation-step level.
You can likely retrieve the defined validation structure for a template, which may let an external system infer:
step names
exercise names
validation steps
You may also retrieve the associated lab guide to get authored instructional content.

What I do not see evidence of today:

No obvious webhook, event stream, SSE, WebSocket, or push-based real-time learner telemetry endpoint.
No clearly exposed API specifically described as:
“current active step”
“learner is viewing/clicking X now”
“lab objective for current step”
“expected outcome of each step” as a dedicated feed
fine-grained in-session activity like browser navigation, command execution, or portal interactions

So, being specific:

Available today

Progress detail endpoint

GET /api/partners/{partnerGuid}/labs/{ondemandLabGuid}/progress/users/{eventUserId}
Best candidate for learner progress tracking.
Likely useful for “how far along is this learner?” rather than “what are they doing this second?”

Progress summary endpoint

POST /api/partners/{partnerGuid}/labs/{ondemandLabGuid}/progress/summary
Aggregate/leaderboard style progress, not detailed live behavior.

Validation-definition endpoint

GET /api/partners/{partnerGuid}/templates/{templateGuid}/template-lab-guide-validations
Gives the authored validation model for the lab template.
Useful for expected checks/steps if your lab uses validations.

Lab guide endpoints

GET /api/partners/{partnerGuid}/labGuide/{labGuideGuid}/partner-lab-guide
GET /api/partners/{partnerGuid}/labGuide/{templateGuid}/template-lab-guides/{onDemandLabGuid}
Useful for the guide content and associations, if you need to map progress back to authored instructions/objectives.
Not clearly available today
Real-time event feed of learner actions
Push notifications when a learner changes step
Dedicated API field for step objective / expected outcome as telemetry
Live “currently doing” feed for external systems
Best-possible external integration pattern today

If you need this now, the likely design is:

Pull lab guide + validation metadata to understand the authored steps/objectives.
Poll the progress detail endpoint for each learner.
Correlate that progress with the guide/validation structure in your external system.

That gives you a derived progress view, but not true real-time behavioral telemetry.

Short answer: not from the APIs I can see here. CloudLabs does expose identifiers for a learner’s deployment, but I do not see an API that hands an external system direct cloud credentials or grants native cloud control-plane access.

What is exposed today from the CloudLabs side:

Per-attendee lab instance records via cloudlabs_labs_instances
Each deployment row includes:
deploymentId — the DID shown in the portal
deploymentUniqueId
cloudUserId — labeled “Cloud DID”
subscriptionFriendlyName
eventUserEmail
status
Per-user registration / launch info via cloudlabs_labs_users
Includes user status and launch link
Deployment troubleshooting logs via cloudlabs_deployment_activity_log
Read-only deployment activity/error log for one attendee deployment
Template / ODL metadata via the metadata tools
Useful to inspect configured VM definitions, licenses, settings, validations, etc.

What I do not see exposed today:

No API surfaced here for:
Azure subscription ID
tenant ID
service principal client ID / secret
managed identity details
AWS access key / secret key / role credentials
GCP service account key / project credentials
a CloudLabs-issued token you can use against Azure Resource Graph, Azure ARM, AWS APIs, or GCP APIs
No endpoint indicating “exchange this lab deployment for cloud credentials”
No external inspection API that proxies native cloud inventory queries on your behalf

Important distinction:

subscriptionFriendlyName is just a display name, not proof of direct API access.
cloudUserId / deploymentId / deploymentUniqueId are CloudLabs identifiers, useful for correlating deployments, not cloud credentials.

So if your question is:

Can an external system inspect the learner’s actual Azure/AWS/GCP resources directly?

Not based on what’s exposed here, unless you already have separate cloud access outside CloudLabs.

To do that, your external system would need credentials obtained independently of CloudLabs, for example:

your own Azure service principal / managed identity with access to the target subscription
your own AWS cross-account role or credentials
your own GCP service account with project permissions

But from the CloudLabs APIs/tools visible here, I do not see a supported path where CloudLabs gives those credentials to the external system.

What you can do programmatically today

You can use CloudLabs to determine:

which learner deployment exists
its deployment/status identifiers
the subscription friendly name
logs/status around provisioning
the authored template/validation structure

You cannot, from what’s visible here, programmatically obtain:

cloud admin credentials
direct subscription/project/account identifiers suitable for native cloud API queries
a built-in CloudLabs resource inventory feed of “what the learner created”
Practical implication

If you need automated inspection of actual learner-created resources, the supported pattern is usually:

Build the lab so resources are created in cloud accounts/subscriptions you control
Use your own cloud credentials outside CloudLabs to inspect those environments
Correlate cloud state back to the learner using CloudLabs identifiers like:
eventUserEmail
deploymentId
deploymentUniqueId
cloudUserId
subscriptionFriendlyName

But CloudLabs itself, from the interfaces available here, does not appear to expose raw cloud credentials to external systems.
