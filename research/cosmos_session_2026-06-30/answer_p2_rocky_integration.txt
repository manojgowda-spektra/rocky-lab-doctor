=== CAPTURED ===
CloudLabs is a platform for designing, provisioning, delivering, and operating hands-on cloud environments for learning and enablement. At a high level: you define a reusable template for an experience, package infrastructure + guide + validations, publish it, wrap it into a delivery format like an on-demand lab, workshop, hackathon, demo, or training event, then CloudLabs provisions per-learner environments and manages access, lifecycle, tracking, and cleanup.

1) What the product does

CloudLabs lets an organization run hands-on technical experiences without making every learner manually build cloud resources from scratch.

Typical use cases:

Labs: self-paced guided exercises
Workshops: instructor-led or scheduled sessions with many attendees
Hackathons: longer-running environments with broader access and team workflows
POCs: controlled proof-of-concept sandboxes for customers or field teams
Demos: curated, often simplified environments for showcasing scenarios
Trainings: structured curriculum with guides, exercises, and completion checks

Across all of these, the product solves the same core problems:

Define the environment once
Provision it consistently
Give each learner isolated access
Attach step-by-step instructions
Validate learner progress
Control cost, timing, and capacity
Clean up afterward
2) The offering types

Think of these as different operational wrappers around the same core lab-delivery engine.

Template

The reusable blueprint. It contains the cloud resources, VM/browser experience, lab guide, validations, and settings.

On-Demand Lab (ODL)

A published, consumable lab definition that users can launch when needed. This is the most common self-service delivery model.

Event / workshop / training

A scheduled or managed delivery construct around labs for a cohort of users. It may include enrollment, timing, capacity, and instructor operations.

Hackathon / POC / demo

Variants of managed lab delivery with different duration, governance, and customization. Same foundation, different packaging and audience expectations.

So the product is not “just labs”; it is a lab operations platform for multiple program types.

3) Full lifecycle: authoring to learner to cleanup
Phase 1: Design

A content author or engineer decides:

what the learner should achieve
what cloud resources are needed
whether they interact directly with Azure/AWS/GCP, through a remote VM, or both
what instructions and checks are required

Artifacts typically include:

IaC: ARM, Terraform, CloudFormation, scripts
VM/app configuration
lab guide content
validation logic
metadata like title, duration, region, platform, permissions
Phase 2: Authoring

In CloudLabs, the experience is assembled into a template:

infrastructure definition
cloud platform mappings
VM configuration if needed
guide/modules/exercises/steps
validation steps
optional licenses, assets, credentials, and advanced settings

This is the reusable source object for the experience.

Phase 3: Publish

The template is published so it becomes available for delivery. After publishing, it can be used to create:

an ODL
an instructor-led event
another managed offering type

Publishing is the point where authored content becomes operationally deployable.

Phase 4: Configure delivery

Operations teams configure how learners will consume it:

availability window
duration
cloud subscription/capacity pool
quotas and concurrency
hot instances / pre-warmed capacity if supported
voucher or registration model
access restrictions/domains
schedules and expiration

At this stage the reusable template becomes an actual offering learners can access.

Phase 5: Registration / assignment

Learners get access through:

direct registration
invitation
voucher
event enrollment
manual assignment by organizer

That creates or associates an event user record, which represents a specific learner in a specific delivery context.

Phase 6: Provisioning

When the learner launches, CloudLabs provisions a lab instance for that learner:

allocates a cloud subscription or sandbox context
deploys cloud resources from the template
prepares the remote VM/browser session if the lab uses one
wires identity/access needed for the lab
records deployment status and diagnostics

This is the important separation:

template/ODL/event = definition and delivery configuration
lab instance = the actual per-learner environment
Phase 7: Delivery to learner

The learner receives a launch experience, commonly:

browser-based remote desktop into a lab VM
direct browser access to a cloud portal/app
credentials/subscription context already prepared
lab guide shown alongside or within the experience

The learner then works through the guide, often module by module.

Phase 8: Guidance and validation

During usage:

the lab guide tells the learner what to do
validations check whether key actions were completed correctly
instructors/support can inspect status and sometimes shadow sessions
telemetry and deployment states help operations troubleshoot failures
Phase 9: Completion / expiration

When the learner finishes or time runs out:

the lab may be marked completed/succeeded
access can expire
resources may be deallocated or deleted based on policy
Phase 10: Cleanup

CloudLabs cleans up:

cloud resources in the learner’s environment
VM sessions
temporary credentials/access
expired instances

Cleanup is essential for cost control and tenant hygiene.

4) How a lab environment is provisioned and delivered

A learner environment usually has three main layers.

A. The cloud environment

This is the actual Azure/AWS/GCP infrastructure used in the exercise:

resource groups, VMs, storage, databases, networks, etc.
deployed from IaC and scripts
isolated per learner or per team, depending on design

CloudLabs typically provisions this into a managed subscription/account/project context allocated for the lab.

B. The access surface

How the learner reaches the environment:

often a browser-based lab VM
sometimes direct access to the cloud portal
sometimes both: use the remote VM to open browser/tools/CLI against the cloud environment

The VM gives CloudLabs a controlled, supportable workspace:

preinstalled tools
known browser state
fewer local-machine issues
easier instructor support/shadowing
C. The control plane

CloudLabs orchestrates everything around the learner:

registration
deployment workflow
launch links
status tracking
validation
time limits
cleanup

So from a learner perspective, they “launch a lab.” Under the hood, CloudLabs is:

identifying the user and entitlement,
allocating capacity,
provisioning cloud resources,
preparing the access workstation/VM if needed,
attaching the guide and validations,
exposing a launch URL.
5) Core concepts and how they relate

Here’s the clean mental model.

Partner

A partner is the top-level organization/tenant operating CloudLabs content.

It owns:

templates
ODLs/events
subscription groups/capacity
courses/content catalog
users and operations data

If you’re thinking in SaaS tenancy terms, partner = customer organization/account boundary.

Template

A template is the reusable master blueprint for a lab experience.

It includes:

cloud deployment definition
VM/browser setup
lab guide
validations
settings and metadata

It is author-facing and reusable. A single template can be used to create multiple delivery offerings.

On-Demand Lab (ODL)

An ODL is a published delivery object derived from a template for self-service or managed access.

It defines how that template is consumed operationally:

title
duration
availability
registration model
vouchers
hot instances
limits and settings

Important: an ODL is not the deployed learner environment. It is the definition learners launch from.

Event

An event is a scheduled or organized delivery context for a group of learners.

It may use one or more lab definitions and adds coordination:

cohort timing
invitations
rosters
instructor operations
session controls

Depending on implementation, an ODL may back an event, or an event may be a broader construct using lab assets and operational settings.

Lab cluster

A lab cluster is best understood as the underlying grouped delivery/provisioning unit used to host or organize lab capacity/environments.

Conceptually it helps CloudLabs:

manage scale
place deployments
organize capacity pools
isolate workloads
support multi-learner delivery

As a new engineer, think of it as infrastructure grouping/orchestration rather than learner-facing content.

Event user

An event user is a learner/attendee within a specific lab or event context.

This record tracks:

identity/email
registration state
deployment state
launch link
entitlement to that specific experience

A person can exist many times as event users across different events/labs.

Lab guide

The lab guide is the instructional content.

It is structured into things like:

modules
exercises
steps
prompts/questions

It explains what the learner does and in what order.

Validation

A validation is a machine-checkable rule or script that verifies learner progress or environment correctness.

Examples:

resource exists
service is configured correctly
app responds on expected URL
command output matches expectation

Validations improve completion tracking and reduce instructor workload.

7) A concrete end-to-end example

Say a team wants an Azure Kubernetes training lab.

A product/content engineer creates a template:

ARM/Terraform to deploy AKS and supporting resources
a Windows or Linux lab VM with kubectl and VS Code
a guide with exercises
validation scripts checking cluster and app state

They publish it.

Operations creates an ODL from that template:

4-hour duration
voucher-based access
allowed for 200 learners
using a subscription group with enough capacity

A learner redeems a voucher and becomes an event user for that ODL.

On launch, CloudLabs:

allocates a subscription
deploys AKS resources
provisions/prepares the learner VM
generates the launch URL

The learner opens the browser-based VM, follows the lab guide, and runs tasks.

Validations confirm they deployed the sample app correctly.

When time ends, CloudLabs marks the deployment completed/expired and cleans up the cloud resources.

That is the full product loop.

8) The key distinctions new engineers should keep straight

These are the ones that matter most:

Template vs ODL

Template = reusable authored blueprint
ODL = published consumable offering based on a template

ODL/Event vs Lab instance

ODL/event = definition and access model
Lab instance = actual deployed environment for one learner

User vs Event user

user = person identity in general
event user = that person’s participation in a specific offering

Guide vs Validation

guide = tells learner what to do
validation = checks whether they did it

VM vs Cloud subscription

VM = learner workstation/access surface
cloud subscription = where the actual cloud resources are deployed
9) Product-engineering view of the system

From an engineering perspective, CloudLabs is really several systems working together:

Content system: templates, guides, validations, assets
Provisioning orchestration: deploy cloud resources and learner workspaces
Identity/enrollment system: event users, vouchers, invitations
Runtime operations: launch, monitor, shadow, retry, support
Cost/capacity controls: subscription pools, hot instances, duration, cleanup
Reporting/state: deployment statuses, completion, failures

That’s the product end to end.

1) What the learner runtime likely looks like, and where Rocky could live

In the common CloudLabs delivery model, the learner launches a browser-based lab session that gives them access to a remote VM/workspace and also needs access to the lab guide. In practice, the experience is usually one of these:

Platform chrome + guide pane + embedded remote session

Lab guide in a platform pane
VM/remote desktop in the main area or adjacent pane
Best Rocky injection points:
platform lab-guide pane augmentation
platform-level sidecar/overlay
This is the cleanest option because Rocky can be aware of the guide and user identity without invading the VM.

Platform page launches a separate remote session/browser tab

Guide may live in CloudLabs page
VM opens separately
Best Rocky injection points:
platform guide pane
browser extension across both tabs
Harder to keep synchronized.

Full-screen browser-based VM

Guide may be outside the VM or opened inside it
Best Rocky injection points:
inside the VM image
browser extension in the VM browser
Most flexible for in-lab assistance, but operationally heavier.
Ranked UI injection options
Easiest: 1) Platform lab-guide pane

Rocky appears as a tab, collapsible assistant, or inline “Ask Rocky” module beside the lab steps.

Pros

Has direct access to guide structure
No VM customization required
Safe and tenant-controlled
Easy to ship incrementally

Cons

Limited visibility into what the learner is doing inside the VM
Help is mostly guide-aware, not action-aware

Best first version.

2) Platform-level overlay / sidecar

A floating assistant across the whole CloudLabs runtime page, potentially aware of guide pane, validation pane, and launch state.

Pros

Better than guide-only
Can follow learner through modules/steps
Can surface proactive tips

Cons

Still blind to most VM activity unless new APIs are added
Needs runtime shell changes

This is probably the best medium-term product shape.

3) Inside the VM image

Rocky is installed as an app, desktop widget, web app shortcut, or browser homepage inside the learner VM.

Pros

Can see local environment if explicitly instrumented
Can help with CLI, files, browser, IDE workflows
Most “hands-on companion” feeling

Cons

OS/image-specific
Harder across Azure/AWS/GCP and Windows/Linux variants
Updating Rocky means updating images or bootstrap scripts
Security/privacy questions become much bigger

Good for advanced scenarios, not ideal as v1.

4) Browser extension

An extension installed in the browser used inside the VM or possibly on the learner’s local browser.

Pros

Can observe cloud-portal navigation and page context
Useful for portal-centric labs

Cons

Browser-dependent
Fragile against portal UI changes
Hard if users switch browsers
More intrusive governance model

Powerful for Azure/AWS console coaching, but brittle.

2) Realistic integration options for Rocky to get context today

Given no real-time event feed today, Rocky should rely on polling, embedded context, and optional VM-side instrumentation.

A. Guide context: realistic today

This is the easiest context source.

Rocky can get:

lab title
module/exercise/step structure
current step the learner is viewing
step instructions/content
expected validation mapping if available

How:

If embedded in the platform guide pane, Rocky can read the rendered guide state directly from the front end
Or CloudLabs exposes a simple runtime API:
GET /runtime/session/{id}/guide
GET /runtime/session/{id}/current-step

This does not require deep platform changes if the guide is already being rendered in the runtime UI.

B. Current step / learner progression: realistic with lightweight platform work

If the platform tracks:

current module
current exercise
current step viewed
step completion/manual check state

Then Rocky can poll that every few seconds.

Without a real-time feed, use:

polling from frontend state
or polling from a backend session endpoint

This is enough for:

“You’re on Exercise 2, Step 4”
“The next action is to open the Azure portal”
“This validation usually fails if the resource group name differs”
C. Validation results: realistic if validation status is exposed

If validations already exist in the runtime, Rocky can consume:

pass/fail
last run timestamp
failure message
validation target/step mapping

Even without events, Rocky can poll:

GET /runtime/session/{id}/validations
or read client state if validations are already shown in the UI

This is extremely valuable because it gives Rocky grounded signals rather than guessing.

D. Real-time observation inside the VM: limited today unless you add instrumentation

Without eventing, Rocky cannot magically “see” what the learner is doing in the VM unless one of these is added:

Option 1: VM-side heartbeat agent

A small agent in the VM reports:

active window/app
current URL in browser
command history snippets
file/project path
terminal exit codes
selected tool state

This can be polled by Rocky backend.

Pros

High-value context
Works even without full event streaming

Cons

New agent install and security review needed
Privacy-sensitive
Cross-platform complexity
Option 2: Browser instrumentation inside VM

A browser extension reports:

current portal page
resource blade
error banners
form state summaries

Pros

Great for cloud-portal labs
Lower scope than full VM agent

Cons

Browser-bound and fragile
Option 3: Command-wrapper tools

For CLI-heavy labs, provide wrapped commands like:

az wrapper
aws wrapper
terraform wrapper

These wrappers log invocation metadata and errors for Rocky.

Pros

Narrow, high-signal
Easier than full desktop observation

Cons

Incomplete coverage
Can feel unnatural if not transparent
E. Shadow/spectate-style help: not enough for autonomous Rocky

If CloudLabs can generate a shadow URL for instructors, that supports human support, but not a fully agentic learner companion unless Rocky has machine-readable access to that stream, which is much harder and likely not appropriate. So I would not design Rocky around visual remote-session observation first.

3) What new platform capabilities CloudLabs would need

Here’s the ranked roadmap from easiest to hardest.

Tier 1 — Easiest, highest ROI

These are the best first investments.

1. Runtime Context API

Expose a stable API for the learner’s active lab session:

session ID
lab/ODL/template identifiers
guide structure
current module/exercise/step
elapsed time / remaining time
learner identity/role
cloud platform

Why it matters:

Lets Rocky be guide-aware immediately
No VM changes needed

Example:

GET /runtime/sessions/{id}/context
2. Validation Results API

Expose validation metadata and latest results:

validation ID
mapped step/exercise
status
error text
last run time

Why it matters:

Gives Rocky trustworthy grounding
Enables step-specific troubleshooting
3. Front-end extension points in the runtime UI

Add official injection points:

assistant panel in guide area
floating sidecar
inline “Ask Rocky about this step”

Why it matters:

Avoids hacks
Makes Rocky a first-class runtime feature
4. Guide semantic model

Store guide content in a structured way, not just rendered HTML/Markdown:

modules
exercises
steps
prerequisites
expected outcomes
hints
linked validations
resource references

Why it matters:

Lets Rocky reason over the guide cleanly
Enables targeted hints instead of generic chat
Tier 2 — Moderate effort, major value

These turn Rocky from “guide chatbot” into “lab companion.”

5. Step progression telemetry

Emit events or at least state changes when learner:

opens a step
marks it complete
runs validation
moves to next exercise

Even polling-friendly storage is enough initially.

Why it matters:

Rocky can be proactive
Rocky can detect stalls
6. Runtime event bus / webhook stream

A proper event stream for:

session launched
deployment succeeded/failed
step changed
validation passed/failed
session nearing expiry

Why it matters:

Removes polling
Enables real-time interventions

This is probably the single most important platform capability after core APIs.

7. Rocky-facing session memory / annotation layer

A service where Rocky can store:

what it already told the learner
learner trouble spots
inferred current task
recommended next action
notes keyed to session + step

Why it matters:

Prevents repetitive help
Creates continuity across the session
8. Structured deployment diagnostics API

For failures, expose:

deployment stage
known error category
remediation hints
resource-level failures

Why it matters:

Rocky can help with provisioning issues before the learner even starts
Tier 3 — Harder, deeper observability

These unlock true in-lab behavioral assistance.

9. VM telemetry agent

Install a supported agent in lab images that reports:

foreground app/window
browser tab metadata
shell command metadata
tool usage
notable errors

Why it matters:

Rocky can understand what the learner is actually doing

Challenges:

OS support
privacy
performance
tenant policy
consent
10. Browser extension framework

Official extension model for the in-VM browser:

URL/page context
cloud portal detection
DOM-level hints on known pages

Why it matters:

Excellent for Azure/AWS/GCP portal coaching

Challenges:

brittle against portal changes
security review
browser/image management
11. In-VM Rocky app / desktop sidecar

A first-class Rocky client inside the lab machine.

Why it matters:

Best learner experience for CLI/IDE workflows
Could support copy/paste of commands, file help, code suggestions

Challenges:

image management
cross-platform support
app lifecycle
security boundary questions
Tier 4 — Hardest / most advanced

These are powerful but expensive and sensitive.

12. Live session computer-use stream

Machine-readable access to the remote desktop session:

screenshots/video frames
OCR
UI state extraction

Why it matters:

Rocky could literally “see” the learner’s screen

Challenges:

very high privacy and infra complexity
latency
model cost
security/governance concerns

This is not where I’d start.

13. Agent action permissions

Let Rocky take actions:

navigate guide
trigger validations
open URLs
prefill commands
maybe execute approved scripts

Why it matters:

Rocky becomes an active copilot, not just advisor

Challenges:

needs trust/safety/approval model
easy to over-automate learning away
Recommended product strategy for Rocky
Phase 1: “Guide-aware Rocky”

Inject Rocky in the platform guide pane or sidecar.

Context sources:

guide structure
current step
validation results
deployment/session status

Capabilities:

explain the current step
summarize what success looks like
interpret validation failures
suggest likely next actions
answer lab-content questions

This is the easiest and most credible v1.

Phase 2: “Session-aware Rocky”

Add:

progression telemetry
runtime event bus
deployment diagnostics
Rocky memory layer

Capabilities:

notice the learner is stuck
remind them of prerequisites
warn on common mistakes
adapt hints based on session history
Phase 3: “In-VM Rocky”

Add either:

VM telemetry agent, or
browser extension, or both

Capabilities:

observe portal/CLI actions
provide just-in-time hints
correlate user behavior with lab steps
Phase 4: “Actionable Rocky”

Add controlled action APIs:

run validation
open correct page
insert suggested commands
maybe perform low-risk remediation with confirmation

Bottom line

If CloudLabs adds only a few things, Rocky can still be useful. The highest-leverage version is a platform-native assistant in the lab guide/runtime shell, powered by:

structured guide context,
current step,
validation results,
session/deployment state.

Without new telemetry, Rocky will be context-aware but not behavior-aware. To make Rocky truly effective in real time, CloudLabs would need to add runtime APIs, step/validation telemetry, and eventually some form of VM or browser instrumentation.
