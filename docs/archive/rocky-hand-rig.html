01

Hand shape & geometry

Rocky has no arms. Like EVE, the hands are detached mitts that hover beside the body, joined to it only by a soft luminous tether — this is what lets them retract fully and reappear, and what keeps the silhouette clean at rest. Each hand is a single readable unit: a rounded palm pad, three short spoke-fingers, and an opposable thumb that only extends for poses that need it (point, thumbs-up). Built from roundRect + arc primitives so it matches the existing body's vector look — no sprites.

Palm pad

Rounded capsule, 22 × 26

The anchor. Drawn at the hand's local origin as a roundRect(-11,-13,22,26,9) with the same body gradient (#fbfdff → #bcc9e0) and a 2px #ffffff66 rim-light on the upper arc. A 14px-blur cyan inner glow keys it to the eyes.

Fingers

3 spokes, len 9, gap 14°

Capsule spokes radiating from the palm's top edge, lineWidth 5, lineCap round, length 9px at rest and extending to 15px when a pose curls or splays them. Fan spread ±14° around the palm's local up-axis.

Thumb

Opposable, default tucked

A 4px spoke off the palm's inner-lower corner. tuck at rest (rotation +70° toward palm, length 5). extend for point/thumbs-up (rotation −20°, length 11). Drives most of the "intent" reading.

Tether

Quadratic wisp, not a limb

A single quadraticCurveTo from the body's shoulder anchor to the wrist, 3px, indigo #6d7cff at 40% alpha, control point pulled toward the body. Stretches and thins with distance; fades to 0 alpha when a hand fully retracts.

Handedness. The two hands are mirror images: the right hand draws with local x un-flipped, the left with ctx.scale(-1,1) on its local frame, so finger fan, thumb, and rim-light all read correctly on both sides. All offsets below are written for the right hand; the left negates every x offset and every rotation.

02

Rest pose & the coordinate frame

All hand positions are body-local: offsets in pixels from Rocky's draw origin (cx, cy), measured before the global scale(0.6) so the rig authors in the same 150×190 body space the eyes use. Positive x is right, positive y is down (canvas convention), rotation is degrees clockwise with 0° = palm facing the viewer, fingers up.

Why offsets, not absolute coords. Rocky roams, leans to the cursor, bobs, and rides a portal entrance. Authoring hands as body-local offsets means a single translate(cx, cy+bob) already inherited from drawRocky carries the hands along for free — the gesture layer never touches screen-space.

Gesture library

Seven poses. Each is a keyframed target for one or both hands plus a hold/loop behaviour. The render loop never jumps to these values — it eases the live hand toward them with the spring in §5, so timing here is the shape envelope, not a per-frame schedule. * point-at-target is the only data-driven pose. Given a screen target (tx, ty) — a failing validation row, a panel control, a lab step — convert to body-local, clamp the wrist to a 64px reach radius around the shoulder anchor, and aim rotation = atan2(ty−wristY, tx−wristX) so the extended index finger points down the line to the target. The fingertip, not the wrist, lands on the aim line.

Emotion coupling

Hands follow the eyes

Fire gestures off the existing setEmotion() calls so hands and eyes stay one creature: thinking→think, celebrate→celebrate, hero→ hands-on-hips power-set (wrist +64,+30, rot +40 in), curious→investigate, panel-open greet →wave. Reassure fires on concerned-after-help.

Restraint

One gesture at a time, budgeted

Hands obey the same attention budget as bubbles — at most one active gesture, auto-releasing to rest after its hold. Loops (wave, celebrate) cap at 3 cycles then settle. In Focus mode, only point/reassure are allowed; the playful set is suppressed.

04

Secondary motion & overlapping action

The single biggest "alive" cue is that hands lag the body. When Rocky moves, the hands don't rigidly travel with him — they trail, overshoot slightly, and settle. This is Disney's overlapping action / follow-through / drag principle: appended parts arrive late and stop late. We get it almost for free with a critically-tuned spring per hand, fed the body's own smoothed position as a moving anchor.

Drag (the lag)

λ = 9, behind the body

Body position uses damp(λ≈2.2). Each hand chases its target with a faster but still-trailing spring; the gap between body and hand during motion is the visible drag. Hands lead-in late and overshoot ~6% on stop.

Velocity skew

Streamline into motion

Offset each hand opposite the body's velocity: wristX −= bodyVx · 0.06, wristY −= bodyVy · 0.06, clamped ±16px. Hands stream behind a fast move and snap forward as it stops — the overshoot reads as weight.

Counter-rotation

Wrist trails the turn

Add rotation += clamp(bodyVx · 0.5, ±12°) so wrists tilt back into a horizontal dash, like a hand dragging through air. Eases out as velocity decays.

Phase offset

Hands aren't twins

Left hand idle-float and any shake run π out of phase from the right (and at 0.96× frequency) so the pair never moves in lockstep — asymmetry is life.

The per-hand spring

A semi-implicit spring beats raw damp() here because it carries velocity — that's what produces the trailing overshoot. Tuned just under critical so it overshoots once and settles in ~320ms, matching the panel-open spring in the v2 spec.

// per hand, per frame — dt in seconds, target in body-local px
const STIFF = 220, DAMP = 26;        // ~3% overshoot, settles ~320ms
function springStep(h, tx, ty, trot, dt){
  // velocity-skew the target by the body's smoothed velocity
  tx -= clamp(body.vx * 0.06, -16, 16);
  ty -= clamp(body.vy * 0.06, -16, 16);
  trot += clamp(body.vx * 0.5, -12, 12);
  for (const ax of ["x","y","rot"]){
    const t = ax==="x"?tx : ax==="y"?ty : trot;
    const a = STIFF*(t - h[ax]) - DAMP*h["v"+ax];   // F = -k·x - c·v
    h["v"+ax] += a * dt;
    h[ax]      += h["v"+ax] * dt;                    // arrives late, stops late
  }
}
Reduced-motion. Under prefers-reduced-motion, drop velocity-skew and counter-rotation, raise DAMP to 40 (no overshoot), and replace looped shakes with a single settle to the pose's mid value. Hands still appear and point — they just don't bounce.

05

Drop-in integration

The rig slots into rocky.html with three additions: a GESTURE table (the §3 data), a drawHand() primitive called twice inside drawRocky before the body so hands sit behind it at rest, and the springStep in the frame loop. It reuses the file's existing damp, roundRect, perf clock, and setEmotion hook.

// 1 — gesture data (subset; full table in §3)
const GESTURE = {
  rest:     { x:86,  y:34,  rot:12,  fl:9,  thumb:"tuck",   both:true  },
  wave:     { x:92,  y:-40, rot:9,   fl:14, thumb:"tuck",   loop:"wave"    },
  point:    { x:null,y:null,rot:null,fl:16, thumb:"extend", aim:true   },
  think:    { x:34,  y:-54, rot:-42, fl:13, thumb:"tuck",   loop:"tap"     },
  celebrate:{ x:78,  y:-72, rot:-30, fl:15, thumb:"extend", both:true, loop:"shake" },
  investigate:{x:44, y:-18, rot:4,  fl:8,  thumb:"extend", lens:true, loop:"sweep" },
  reassure: { x:70,  y:6,   rot:-6,  fl:13, thumb:"extend", both:true },
};

// 2 — one hand, local frame already at wrist; side = +1 right / -1 left
function drawHand(side, fl, thumb){
  ctx.scale(side, 1);                                // mirror the left
  // palm
  ctx.shadowColor="#38e1ff"; ctx.shadowBlur=14;
  const g=ctx.createLinearGradient(0,-13,0,13);
  g.addColorStop(0,"#fbfdff"); g.addColorStop(1,"#bcc9e0");
  ctx.fillStyle=g; roundRect(-11,-13,22,26,9); ctx.fill();
  // 3 fingers fanned ±14° off local up
  ctx.shadowBlur=0; ctx.lineWidth=5; ctx.lineCap="round"; ctx.strokeStyle="#eaf0fb";
  [-14,0,14].forEach(deg=>{ const a=(deg-90)*Math.PI/180;
    ctx.beginPath(); ctx.moveTo(0,-11);
    ctx.lineTo(Math.cos(a)*fl, -11+Math.sin(a)*fl); ctx.stroke(); });
  // thumb (tuck vs extend) + optional magnifier ring for investigate
  drawThumb(thumb);
}

// 3 — in frame(): chase targets behind the body, then draw
const tgtH = resolveGesture(activeGesture, mouse);    // §3 + aim math
springStep(handR, tgtH.x,  tgtH.y,  tgtH.rot,  dt);
springStep(handL, -tgtH.x, tgtH.y, -tgtH.rot,  dt);  // mirror x & rot
Draw order. Call both hands at the top of drawRocky (before the body ellipse) so at rest they tuck behind Rocky's silhouette and only their outer edge shows. Poses that lift the hands above y < −30 draw them after the body instead, so a wave or celebrate reads in front — switch by the live wrist y, not the target, so the layer flips mid-arc.

06

Sources & lineage

Design references for the hand language and the motion principles behind the timing choices:

Character lineage

EVE · BD-1 · Cozmo

EVE (WALL·E, Pixar 2008) — detached hovering hands joined by no visible arm; the core silhouette idea. BD-1 (Star Wars Jedi, Respawn) — expressive intent from minimal jointed parts. Cozmo / Vector (Anki) — a single lift arm carrying a full emotional vocabulary; the "one part, much meaning" economy.

Animation principles

Overlapping action & drag

Thomas & Johnston, The Illusion of Life (Disney, 1981) — follow-through, overlapping action, slow-in/slow-out: appended parts lag and settle late. This is the basis for §4's per-hand spring trailing the body.

Social-robot gesture

Deictic & legible motion

Deictic (pointing) gesture and "legibility" in HRI — Cynthia Breazeal's Designing Sociable Robots (MIT, 2002) and work on legible robot motion (Dragan & Srinivasa) — gestures should telegraph intent before completion. Point/reassure are built to be readable at their halfway frame.

Motion feel / timing

Springs over linear tweens

Spring dynamics for UI (the "stiffness / damping / mass" model popularised by iOS UIKit dynamics & react-spring) — the 220/26 constants and ~3% overshoot mirror the panel-open spring already specified in Rocky's v2 interaction spec.

Grounded against the live build: coordinate frame, damp() smoothing, roundRect, the emotion table, and the investigate/hero beats are read directly from source/rocky-prototype/web/public/rocky.html and docs/rocky_living_presence_interaction_spec.html.
